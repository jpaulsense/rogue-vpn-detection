The analyst playbook needs a baseline, not more collection

Eleven layers of evidence per device already land in XSIAM every night. None of them answer an analyst's question, because no layer knows what that device normally looks like.

Device location / VPN spoofing · 2026-11-09 · measured sourced assumed mark every claim below

The answer

Build one thing: a per-device baseline, held in a lookup, written by the sweep that already runs. Every other ask follows from it. The verdict an analyst reads, the case that gets opened, the confidence score and the map all come from comparing tonight's scan to what that device has always looked like.

No new collection. No machine learning. The comparison is a set membership test on four axes and about forty lines in an automation that is already deployed.

The detection today emits 41 observables per device per night. An analyst handed first_public_hop = 192.77.111.1 and dns_servers = 100.100.100.100|172.20.0.1 has no way to judge them. The same two values next to never seen before on this device, which has reported 207.173.132.1 on 47 of 47 scans across 31 days is a finding anyone can action.

The scale case makes this sharper rather than softer. In an estate with many egress points, no global list of good IP addresses can exist, and a central allow-list becomes a maintenance project that is always behind. A device compared against itself needs no such list, and the per-device test is the same test whether the fleet has ten machines or ten thousand.

The collection layer is finished. Everything in this plan sits downstream of the row that already lands in that dataset every night.

What this optimizes for when goals conflict

  1. A device is compared to itself, never to the fleet. Hotel wifi in Sacramento is slower than fibre in Austin, and a regional office is not an anomaly. Every threshold that is global is wrong at the second site.
  2. Silence until the baseline is earned. A device with four days of history produces no finding at any confidence. A detection that fires on every new laptop is turned off within a week.
  3. The case carries the reasoning, not the fields. If an analyst has to reconstruct why something was elevated, the detection has pushed its work onto them.
  4. Prefer a signal that cannot be spoofed over one that is convenient. Ranked: RF environment, then clock, then reachability, then egress address. Egress is the weakest and the easiest to read, which is why it is where everyone stops.
  5. No enrichment call from an endpoint. A key that ships to an endpoint is a published key. Geolocation happens server side or not at all.

Normal is per device, and it belongs in a lookup

For each device, over a trailing 30 days, the baseline holds the set of values observed on each axis with how often each was seen, plus how much history backs it.

The strongest axis is dark on macOS. measured Every macOS row since 2026-11-06 reports wifi_method: none and bssid_count: 0: Apple gates BSSID on Location Services authorization for the calling process and root does not satisfy it. A Mac is therefore a three-axis detection and a Windows machine is a four-axis one. Stormbreaker returns 1 to 7 BSSIDs per run under SYSTEM with nobody logged in.

Why a lookup is right here, having been wrong before

A lookup has no _time and ignores the query timeframe, which is what made it the wrong home for scan history and produced a dashboard showing a frozen Saturday. The baseline is the opposite shape: one small mutable row per device, read by joining, never plotted over time. That is a reference table, which is what a lookup is.

Who writes it

The sweep automation, at the end of its run, from one XQL query over the raw dataset. The tenant already carries an XQL Query Engine integration instance, so the automation can run XQL through xdr-xql-generic-query without a second credential measured. The baseline is recomputed nightly rather than incremented, which costs one query and removes a whole class of drift bug.

A device that has genuinely relocated, a person who moved house, will pull its own baseline across within the window. That is correct behaviour, and it is also the weakness: a slow move is invisible by construction. Section Three reasons this fails takes this up.

The deviation test, and the gate in front of it

For the newest scan on each device, each axis is a set membership test against that device's own baseline. There is no model, no training and no threshold tuning.

egress_new       = first_public_hop not in baseline.egress_values
asn_new          = ip_asn            not in baseline.asn_values
rf_disjoint      = bssid_set and baseline.bssid_set and no overlap
clock_changed    = timezone_key      not in baseline.timezone_values
reach_dropped    = anycast_reachable == 0 and baseline.anycast_typical > 0

Confidence is how many independent axes moved, which is a count rather than a weighting. Two axes moving together is far harder to produce accidentally than either alone.

Axes movedBaseline matureBaseline immature
0no findingno finding
1LOW, recorded, no casesuppressed
2MEDIUM, casesuppressed
3 or moreHIGH, case, prioritysuppressed

Mature means 14 days and 10 scans assumed, a starting value to be moved once a month of real data exists. Until a device qualifies it appears on the dashboard as building baseline with its day count, which is a state an analyst can see rather than an absence they cannot.

The test case, which is already in the data

The MacBook Air has been seen behind two egress points, 192.77.111.1 and 207.173.132.1, while every other device stayed at one measured. Taking it out of the house and back is a repeatable end-to-end test of the whole chain, on a device whose baseline is the most established in the fleet.

What the analyst opens

There is no create-a-case API on Cortex and none is needed: a correlation rule over a custom dataset produces the issue, and alert_fields is what makes it readable sourced, xsiam-xql-correlation skill, verified on tenant. A correlation rule may source any custom dataset and may not source issues or alerts, which decides the shape below.

The narrative is composed where the comparison happens

Only the automation holds both sides at once, so it writes the sentence rather than the rule. The finding row carries a summary field, and alert_fields maps it onto the case description.

Three properties worth keeping as the format changes: every claim names what normal was, the unchanged axis is stated rather than omitted, and the maturity of the baseline is on the face of the case so an analyst can discount a thin one.

The map, and what it needs that we do not yet have

Map is a real graph type. The full set is Area, Bubble, Column, Funnel, Gauge, Line, Map, Pie, Scatter, Single Value and Word Cloud sourced, Graph query results, verified byte exact 2026-11-09. The documentation names the option and does not state what fields it binds to, which is the first thing to settle on the tenant.

The detection has two possible location sources and both are currently empty on a fleet run:

SourcePrecisionCostState today
Wi-Fi fix from BSSIDsTens of metresGoogle Geolocation per deviceDead on macOS; Windows only
IP geolocation of the egress addressCity, sometimes worseOne lookup per distinct egress addressNeeds enrich, currently off

Enrichment is off by default so that no key reaches an endpoint and no third party is called from a laptop. Both survive if the automation enriches server side, and the egress address is the cheap one: the fleet shares egress points, so ten devices cost two lookups, not ten. Resolve distinct egress addresses once per night, cache them in a lookup, and the map costs a handful of calls a day.

Reserve the Wi-Fi fix for a device that has already deviated, where tens of metres is worth a call and the question is which building rather than which city.

A map answers orientation, not the question. Whether a device left California is decided by the baseline comparison, which works with no coordinates at all. The map is for the analyst looking at a fleet of thousands and asking where the outliers are, and for the screenshot that makes the finding legible to someone who was not in the console.

Three reasons this fails

1. A determined user moves one axis, and one axis is not a case

Keep the laptop's timezone set to Pacific, use a VPN that terminates on the same ASN, and on a Mac, where the RF axis is already dark, only reachability is left. The gate that suppresses single-axis findings to keep the false-positive rate survivable is the same gate that lets this through. Windows carries the signal that closes it, and the honest statement to a customer is that this is strong on Windows and partial on macOS.

2. Daily cadence has holes a trip fits through

One scan a night means a device that leaves and returns inside 24 hours is never seen away. Script execution actions expire after four days, so a laptop that stays closed produces nothing, and its last row looks exactly like a current reading unless scanned_at is on the face of the widget. Raising the cadence raises the compute-unit cost and is the obvious lever, but not before a week of daily data says what the quiet hours look like.

3. Egress is a property of the network, not the person

A corporate VPN, SASE, or any centralised egress makes every device look like it is at the egress point, and the axis goes quiet for the whole fleet at once. The opposite failure is worse: in an estate with many egress points, roaming between offices moves the egress axis routinely, so the false-positive rate is set by how often people travel for work rather than by how often anyone does anything wrong. Both are arguments for ranking RF and clock above egress, and for never shipping a single-axis egress alert.

Verify on the tenant before building

  1. What the Map graph type binds to. Country name, region, or a lat and long pair. Decides whether IP geolocation is sufficient or coordinates are required. Read the viewOptions of a map widget that already renders somewhere on the tenant.
  2. Whether a correlation rule can join a lookup. If it can, the deviation test could live in the rule rather than the automation and the findings dataset disappears. The design above assumes it cannot, which is the safe assumption and the more testable one.
  3. Whether a second HTTP collector is needed. A collector's dataset is fixed at creation, so findings in their own dataset means a second console step. Findings in the existing dataset behind a record_type filter avoids it and makes the correlation rule re-evaluate scan rows it does not care about.
  4. Compute-unit cost of the nightly XQL recompute. API queries meter against the tenant allowance. One query a night is unlikely to matter and should be measured rather than assumed.

Why the raw dataset and not the lookup, restated once

A lookup has no _time, ignores the query timeframe, is mutable and has no retention policy. The raw dataset has a native time axis, honours the dashboard time picker, is append only and ages out. History goes in the raw dataset. The baseline, being one small mutable row per device read by joining, goes in a lookup.
